GA4データをBigQueryへ

GA4 の BigQuery エクスポートを設定すると、1イベント1行の生データが毎日 BigQuery に届きます。この章では設定の手順、届くテーブルの構造、そして GA4 データ特有の UNNEST を使った SQL を、このリポジトリのデータで練習します。

この章の内容

  1. エクスポートを設定する
  2. 届くテーブル
  3. 1行の中身（スキーマ）
  4. UNNEST の考え方
  5. GA4 画面と数字が合わない理由

  7. 運用: ビューと定期実行

エクスポートを設定する

このリポジトリのプロパティでは設定済みです。新しく設定するときの手順を残しておきます。

  1. 権限と GCP プロジェクトを用意する

    GA4 プロパティの編集者以上の権限と、GCP プロジェクトのオーナー権限が必要です。プロジェクトで BigQuery API が有効になっていることを確認します。ストリーミングを使う場合は課金アカウントの紐づけも必要です。

  2. GA4 側でリンクを作る

    管理サービス間のリンク設定BigQuery のリンク で「リンク」を押し、プロジェクトを選びます。メニューの表記は UI の更新で変わることがあり、以前は「プロダクトのリンク設定」でした。

  3. オプションを選ぶ

    データのロケーションasia-northeast1（東京）
    後から変えられない。結合したい他のデータと同じ場所にする
    データストリームとイベント対象のストリームを選ぶ。不要なイベントを除外できる
    頻度毎日（無料、翌日に前日分）と ストリーミング（有料、数分遅れ）。両方選べる
    ユーザーデータユーザー単位のテーブル（users_ / pseudonymous_users_）も出すか

  4. 送信して翌日を待つ

    データセット analytics_<プロパティID> が自動で作られ、翌日から日次テーブルが入り始めます。プロジェクトには firebase-measurement@system.gserviceaccount.com というサービスアカウントが自動で追加されます。これを消すとエクスポートが止まります。

上限とコスト
  • 標準（無料）プロパティの日次エクスポートは1日100万イベントまでです。継続して超えると日次エクスポートが一時停止します。イベントの除外で減らします。
  • ストリーミングには件数の上限はありませんが、BigQuery のストリーミング挿入として課金されます。完全性の保証もありません。使い終わったらオフにします。

届くテーブル

テーブル内容届くタイミング
events_YYYYMMDDその日の全イベント。1行1イベント日次。前日分が翌日に届く（無料）
events_intraday_YYYYMMDD当日分の途中経過ストリーミング。数分遅れ（$0.05/GB 相当）。日次テーブルができると消える
pseudonymous_users_YYYYMMDDuser_pseudo_id ごとの最新の属性ユーザーデータのエクスポートを有効にした場合
users_YYYYMMDDuser_id ごとの最新の属性同上。user_id を送っている場合

日付はプロパティのタイムゾーン（管理画面の設定）で区切られます。

1行の中身（スキーマ）

主な列です。[] は ARRAY、{} は STRUCT を表します。

event_date                 STRING   '20260401'（プロパティのタイムゾーン）
event_timestamp            INT64    マイクロ秒の UNIX 時刻（UTC）
event_name                 STRING   'button_click'
event_params[]             ARRAY<STRUCT>
  ├─ key                   STRING   'button_name'
  └─ value {}
       ├─ string_value     STRING   '資料ダウンロード'
       ├─ int_value        INT64    （整数で送った値）
       ├─ float_value      FLOAT64  （ほぼ使われない）
       └─ double_value     FLOAT64  （小数で送った値）
user_id                    STRING   gtag の user_id

user_properties[]          ARRAY<STRUCT>  key / value{string_value, int_value, …, set_timestamp_micros}

GA4 画面との一番の違い

送ったパラメータはカスタムディメンションに登録していなくても、すべて event_params に入っています。値の型によって入る列が変わるのにも注意します。price: 8000 は int_value、price: 8000.5 なら double_value、"8000" と文字列で送れば string_value です。

UNNEST の考え方

2つの書き方

-- 書き方1: FROM で UNNEST して WHERE で key を絞る（パラメータ1つだけ見たいとき）
SELECT ep.value.string_value AS page_location, COUNT(*) AS pageviews
FROM `big-query-sample-492309.analytics_324810718.events_*`,
  UNNEST(event_params) AS ep
WHERE _TABLE_SUFFIX BETWEEN '20260301' AND '20260401'
  AND event_name = 'page_view'
  AND ep.key = 'page_location'
GROUP BY page_location;

-- 書き方2: SELECT の中のサブクエリで1つずつ取り出す（複数のパラメータを列にしたいとき。おすすめ）
SELECT
  event_name,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'button_name') AS button_name,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'section') AS section
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20260301' AND '20260401'
  AND event_name = 'button_click';

書き方2なら1イベント1行のまま、パラメータを列として並べられます。行が増えないので集計を間違えにくいです。

GA4 画面と数字が合わない理由

理由内容
集計方法GA4 画面のユーザー数は HyperLogLog++ による推定値。BigQuery の COUNT(DISTINCT) は正確な値なので少しずれる
しきい値・モデリングGA4 画面は少人数データの非表示や、同意していないユーザーの推計を含むことがある。BigQuery は届いた生データだけ
レポート IDGA4 画面は User-ID やシグナルでユーザーをまとめる。BigQuery で何を数えるかは自分で決める
タイムゾーンevent_date はプロパティのタイムゾーン、event_timestamp は UTC
当日分日次テーブルは翌日にならないと届かない

完全一致を目指すより、「傾向が合っていればよい」「正確なユーザー単位の履歴は BigQuery が正」と役割を分けて考えます。

SQL レシピ集

すべてこのリポジトリのデータセットでそのまま動きます。期間は「直近7日」にしてあります。BETWEEN の日付指定には当日分の events_intraday_ テーブルは入りません（_TABLE_SUFFIX が intraday_2026… という文字列になるため）。

1. 届いているパラメータを全部洗い出す

何がどの型で届いているかを最初に確認します。カスタムディメンションの登録漏れもこれで分かります。

SELECT
  event_name,
  p.key,
  COUNT(*) AS cnt,
  COUNTIF(p.value.string_value IS NOT NULL) AS as_string,
  COUNTIF(p.value.int_value IS NOT NULL) AS as_int,
  COUNTIF(p.value.double_value IS NOT NULL) AS as_double
FROM `big-query-sample-492309.analytics_324810718.events_*`,
  UNNEST(event_params) AS p
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
GROUP BY event_name, p.key
ORDER BY event_name, cnt DESC;

2. 取り出し用の一時関数を作る

毎回サブクエリを書くのが面倒なら、クエリの先頭で一時関数を定義します。

CREATE TEMP FUNCTION param_str(params ANY TYPE, k STRING) AS (
  (SELECT value.string_value FROM UNNEST(params) WHERE key = k)
);
CREATE TEMP FUNCTION param_int(params ANY TYPE, k STRING) AS (
  (SELECT value.int_value FROM UNNEST(params) WHERE key = k)
);
-- 型が分からない値を文字列でまとめて取る
CREATE TEMP FUNCTION param_any(params ANY TYPE, k STRING) AS (
  (SELECT COALESCE(value.string_value, CAST(value.int_value AS STRING),
                   CAST(value.double_value AS STRING), CAST(value.float_value AS STRING))
   FROM UNNEST(params) WHERE key = k)
);

SELECT
  param_str(event_params, 'button_name') AS button_name,
  param_str(event_params, 'section') AS section,
  param_str(user_properties, 'plan') AS plan,
  COUNT(*) AS clicks
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
  AND event_name = 'button_click'
GROUP BY button_name, section, plan
ORDER BY clicks DESC;

02章で探索に作った「ボタン名 × プラン」の表と同じものが、登録なしで作れます。

3. ユーザープロパティ別のユーザー数

SELECT
  (SELECT value.string_value FROM UNNEST(user_properties) WHERE key = 'plan') AS plan,
  (SELECT value.string_value FROM UNNEST(user_properties) WHERE key = 'user_type') AS user_type,
  COUNT(DISTINCT user_pseudo_id) AS users,
  COUNT(*) AS events
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
GROUP BY plan, user_type
ORDER BY users DESC;

4. 日別のユーザー数・セッション数・PV

セッションは user_pseudo_id と ga_session_id の組み合わせで1つと数えます。

SELECT
  PARSE_DATE('%Y%m%d', event_date) AS day,
  COUNT(DISTINCT user_pseudo_id) AS users,
  COUNT(DISTINCT CONCAT(user_pseudo_id, '-', CAST(
    (SELECT value.int_value FROM UNNEST(event_params) WHERE key = 'ga_session_id') AS STRING
  ))) AS sessions,
  COUNTIF(event_name = 'page_view') AS page_views
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
GROUP BY day
ORDER BY day;

5. 1人のユーザーの行動履歴（日本時間）

GA4 のユーザーエクスプローラと同じことを、しきい値や (other) の影響なしで行えます。

SELECT
  DATETIME(TIMESTAMP_MICROS(event_timestamp), 'Asia/Tokyo') AS jst,
  event_name,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'page_title') AS page_title,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'button_name') AS button_name,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'item_name') AS item_name
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
  AND user_id = '22222222-bbbb-4bbb-8bbb-222222222222'
ORDER BY event_timestamp;

6. ファネル（商品を見た → カートに入れた → 購入した）

ユーザーごとに各ステップの最初の時刻を取り、順番どおりに進んだ人を数えます。

WITH steps AS (
  SELECT
    user_pseudo_id,
    MIN(IF(event_name = 'view_item', event_timestamp, NULL)) AS t_view,
    MIN(IF(event_name = 'add_to_cart', event_timestamp, NULL)) AS t_cart,
    MIN(IF(event_name = 'purchase', event_timestamp, NULL)) AS t_purchase
  FROM `big-query-sample-492309.analytics_324810718.events_*`
  WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                          AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
  GROUP BY user_pseudo_id
)
SELECT
  COUNTIF(t_view IS NOT NULL) AS step1_view_item,
  COUNTIF(t_cart > t_view) AS step2_add_to_cart,
  COUNTIF(t_purchase > t_cart AND t_cart > t_view) AS step3_purchase
FROM steps;

比較の片方が NULL だと結果も NULL になり、COUNTIF では数えられません。そのため「前のステップを踏んでいない人」は自然に除外されます。

7. gtag.js と GTM の比較

04章で GTM の Google タグに tag_source = gtm を付けたので、どちらから来たデータかを見分けられます。

SELECT
  IFNULL((SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'tag_source'),
         'gtag.js（index.html）') AS source,
  event_name,
  COUNT(*) AS events
FROM `big-query-sample-492309.analytics_324810718.events_*`
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
GROUP BY source, event_name
ORDER BY source, events DESC;

8. e コマースの items を展開する

gtm.html の「カートに追加」は items 配列付きで送っています。index.html の add_to_cart は item_name をただのイベントパラメータで送っているので、items は空です。

SELECT
  event_name,
  item.item_id,
  item.item_name,
  item.price,
  item.quantity
FROM `big-query-sample-492309.analytics_324810718.events_*`,
  UNNEST(items) AS item
WHERE _TABLE_SUFFIX BETWEEN FORMAT_DATE('%Y%m%d', DATE_SUB(CURRENT_DATE('Asia/Tokyo'), INTERVAL 7 DAY))
                        AND FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
  AND event_name = 'add_to_cart';

9. 今日のデータを見る（ストリーミング有効時）

SELECT event_name, COUNT(*) AS cnt
FROM `big-query-sample-492309.analytics_324810718.events_intraday_*`
WHERE _TABLE_SUFFIX = FORMAT_DATE('%Y%m%d', CURRENT_DATE('Asia/Tokyo'))
GROUP BY event_name
ORDER BY cnt DESC;

日次テーブルと当日分を一緒に見たいときは、events_* と events_intraday_* を UNION ALL します。events_* だけで _TABLE_SUFFIX を絞らずに書くと、日次と当日分が両方入って二重に数えることがあります。

運用: ビューと定期実行

平らにしたビューを作る

よく使う列を取り出したビューを作っておくと、Looker Studio やほかの人のクエリが簡単になります。

CREATE OR REPLACE VIEW `big-query-sample-492309.tutorial.events_flat` AS
SELECT
  _TABLE_SUFFIX AS table_suffix,
  PARSE_DATE('%Y%m%d', event_date) AS event_date,
  DATETIME(TIMESTAMP_MICROS(event_timestamp), 'Asia/Tokyo') AS event_datetime_jst,
  event_name,
  user_pseudo_id,
  user_id,
  (SELECT value.int_value FROM UNNEST(event_params) WHERE key = 'ga_session_id') AS ga_session_id,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'page_location') AS page_location,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'button_name') AS button_name,
  (SELECT value.string_value FROM UNNEST(event_params) WHERE key = 'tag_source') AS tag_source,
  (SELECT value.string_value FROM UNNEST(user_properties) WHERE key = 'plan') AS plan,
  device.category AS device_category,
  geo.city AS city
FROM `big-query-sample-492309.analytics_324810718.events_*`;

ビューは中身を保存しないので、使うたびに元のテーブルを読みます。使う側でも table_suffix で期間を絞り、ドライランで処理量を確かめます。データセット tutorial は GA4 のデータセットと同じリージョンに作ります（05章）。

定期実行（スケジュールされたクエリ）

エディタの「スケジュール」から、毎朝前日分を集計して別テーブルに追記する、といった処理を登録できます。集計済みテーブルを Looker Studio から読むようにすると、表示が速くなり、スキャン量も減ります。

止めるときは

学習が終わったら、管理サービス間のリンク設定BigQuery のリンク からストリーミングをオフにします。日次エクスポートは無料なので残して構いません。
